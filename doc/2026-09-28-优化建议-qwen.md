# TokenBar 代码审查与优化建议

> 日期：2026-09-28
> 范围：macOS 端（mac/Sources/TokenBar/）+ Windows 端（windows/src/TokenBar/）全量审查
> 状态：建议稿，未实施

## 总体评价

基础设施层质量明显高于平均水平：密钥三态读写（防"读不到→误删"）、CAS 刷新闸门、generation 防脏写、共享 HttpClient、原子写 settings.json、两端共享测试黄金向量，这些都很规范。主要问题集中在：**确认的并发/资源 Bug（Windows 端为主）**、**Provider Service 层大量模板复制**、**巨石 UI 文件**、**I18n 双轨制**、以及**编排层测试零覆盖**。

## P1 · 结构性重复（最大的维护负担）

### 11. 九个 Provider Service 无统一抽象，模板代码各复制 5-8 份（两端同病）

没有 `QuotaProvider` 之类的协议/接口，每个 Service 都是独立 singleton + 不同形状的元组返回值。逐条确认的重复：

- **`getHeader`/`GetHeader` 大小写不敏感取响应头闭包**：mac 复制 6 份（OpenAI:88-96、DeepSeek:66-74、Kimi:73-81、Volcengine:58-66、Claude:381-389、Custom:160-168,276-284）；win 复制 5 份。且完全多余——`HTTPURLResponse.value(forHTTPHeaderField:)` 本身就大小写不敏感（GLMService.swift:64-70 已在直接用）。
- **endpoint trim + 去尾斜杠块**：mac 复制 8 份。
- **401/429/非 2xx 三段式错误处理 + `isZh ? 中文 : 英文` 内联**：每个服务复制一遍（mac ≥7 处、win ≥6 处），且这套错误文案**绕过了 I18n 系统**，与 RefreshManager 用的 I18nKey 是两套并行机制。
- **x-ratelimit 三头 → TPM 窗口构造块**：mac 复制 5 份（连 clamp 表达式都逐字相同）、win 复制 4 份。
- **余额查询重复实现**：`DeepSeekService.fetchBalance` 与 `CustomProviderService.fetchDeepSeekBalance` 是同一段代码；`KimiService.fetchBalance` 与 `fetchMoonshotBalance` 同理。
- **key 尾号掩码逻辑**：`cleanKey.count > 6 ? suffix(4) : cleanKey` 复制 5 份。

**建议方向**：抽 `protocol QuotaFetching`（win 端对应 interface）+ 共享的 `RateLimitHeaderParser`、`EndpointNormalizer`、`ProviderError`（携带 I18nKey 而非内联双语文案），两端同步收敛。

### 12. RefreshManager 两端各有 9-10 个逐行雷同的 `refreshXxx()`

- mac：`RefreshManager.swift:636-1259`，每个约 45-60 行（置 loading → 查 key 空 → 调 service → 写窗口 → 错误分类 → commit），GLM/OpenAI/DeepSeek/Volcengine/Kimi/OpenRouter 六个几乎只差字段名。
- win：`RefreshManager.cs:796-1449`，同样结构，每加一个厂商要复制 ~50 行。
- win 端该文件还同时承担：定时器、网络监听、settings 持久化、凭据同步、余额提醒状态机与托盘气泡、本地导入——至少 SettingsStore、SecretSync、BalanceMonitor 可拆出。

**建议方向**：收敛成"provider 描述符 + 单一表驱动执行器"。

### 13. SettingsView.swift（2651 行）巨石文件

- 12 个 tab 全部内联在一个 struct：~35 个 @State（:23-105）+ 25 条 settings→input 的 onChange 同步（:260-284）+ 12 个 tab 完整 UI（:399-2594）。
- 每个厂商 tab 是 130-200 行的同构模板（标题卡 + 状态卡 + SecureField/eye 切换 + endpoint + 保存并测试按钮）。
- **新增一个设置字段要同时改 5 处**（init/syncFromSettings/onChange/@State/tab UI），漏一处就是"设置不生效"类 bug——代码注释（:296-301）已记录过一次真实故障。
- 混合职责：`ProviderTabPicker`（NSViewRepresentable）、`startGeminiGoogleLogin`、`saveAliyunAccessKeyAndTest` 等业务编排也在同一文件。

**建议方向**：拆成每 tab 一个子 View（自带自己的 @State），可直接消掉三份手工同步清单。

同类问题（程度较轻）：`GeminiService.swift`（1115 行）一个 actor 负责 OAuth client 发现、loopback 登录、token 刷新、Antigravity 配额、AI Studio Key、本地文件解析、凭证合并七件事，凭证获取子系统适合独立成 `GeminiCredentialResolver`。win 端 `SettingsWindow.xaml.cs`（1471 行）/`PopoverWindow.xaml.cs`（906 行）手写视觉树、无 MVVM，两段卡片构造逻辑 ~70% 重复。

### 14. 窗口标题用中文串当翻译 key

- mac：`TokenQuota.swift:168-195` `localizedTitle` 靠匹配中文标题反译（含 `"可用模型 ("` 前缀裁剪这种脆弱逻辑），default 分支直接返回中文——新标题忘了登记就在英文模式漏中文。
- win：`TokenQuota.cs:127-168` 同款，`BadgeLabel` 靠 `Contains("月")/Contains("周")` 推断。
- 任何 service 改标题措辞都会**静默破坏**英文界面。

**建议方向**：Title 改语义枚举（`enum WindowTitle { case fiveHour, weekly, monthly, ... }`）随 TokenWindow 持久化，显示层再翻译。

## P2 · UI 性能（win）

### 15. Popover 隐藏时仍全量重建视觉树

- RefreshManager 每轮触发 ≥20 次 `NotifyQuotasUpdated`（round 开始、每个 provider 开始/结束、round 结束）。
- `PopoverWindow` 关闭被拦成 Hide（PopoverWindow.xaml.cs:44-49），事件订阅只在 Closed 才解除（:51-57），**隐藏状态下每次通知仍执行 `RenderCards` 整棵视觉树重建**（:87-166，先 `Children.Clear()` 再 new 全部 Border/Grid）。
- SettingsWindow 同理：`UpdateStatuses`（:609-652）每次都 `RenderCustomProvidersList()` 重建全部卡片，即使 Custom tab 不可见。

**建议方向**：不可见时跳过渲染（IsVisible 检查或 dirty 标记），或改 ItemsControl+DataTemplate 增量更新。

### 相关（mac）：provider 刷新体全在 MainActor

`RefreshManager.swift:446-499`：`withTaskGroup` 里每个子任务都是 `@MainActor`，9+ 个厂商的 JSON 解析、窗口构造全部在主线程串行（网络等待会让出，CPU 段不会）。当前响应体小无碍，但大响应（如 `/models` 返回数百模型）会卡 UI，属设计上限。

## P3 · 测试补强

### 16. 两端测试全在纯函数层，编排层与网络层零覆盖

已覆盖（质量不错）：TokenWindow 计算/角标/过期、Claude 本地解析、Aliyun 全家桶（Signer 黄金向量、6 种响应形状、错误分类）、Gemini 凭证合并、Kimi coding 4 种形状、SecretLookup/SaveAction 三态、withTimeout、AppSettings 编解码兼容等。

**未覆盖的关键逻辑**：

- RefreshManager 核心机制：闸门抢占、generation 代数丢弃、超时收尾、首刷退避、网络恢复补刷——**注释里自述修过 3 次线上事故的最复杂逻辑，零测试**。
- mac `processBalance` 低余额提醒状态机（阈值→1.2× 复位）。
- 所有 Service 的 HTTP 层：无 URLProtocol stub，401/429 分类、响应头解析全无测试。
- win 端多数解析器是 `private`，测试根本够不到：ClaudeService `~/.claude.json` 解析、GeminiService `ParseQuotaBucket`、GLMService `/quota/limit` 解析（含秒/毫秒量级判断——恰是与 mac 有分类顺序差异的地方）。

**建议方向**：Kimi/Aliyun 已示范正确做法（`internal static` 纯函数 + `InternalsVisibleTo`），把 Claude/Gemini/GLM 解析器照此改造即可低成本补测。

### 17. mac 132 个测试挤在一个 2105 行文件

`TokenBarTests.swift` 单个 `final class`，按模块拆分成多个 XCTestCase 文件是零成本改进。另建议加一条"每个 I18nKey 在 zh/en 下都非空且不等于 rawValue"的一致性测试。

## P4 · 安全与其他

### 密钥存储（现状良好，两点需知悉）

- mac：钥匙串（`kSecAttrAccessibleAfterFirstUnlock`）；win：Win32 凭据管理器（受 DPAPI 保护）。三态读写、防误删、日志纪律好（全库 grep 未发现 key/token 插值进日志）。
- **明文兜底是设计内行为但风险真实**：钥匙串/凭据管理器不可用时，全部 API Key、OAuth token、Cookie 明文写入 plist / settings.json（mac TokenQuota.swift:953-964；win AppSettings.cs:136-140）。可考虑对 `claudeToken`/`geminiRefreshToken` 这类长效 OAuth 凭证不回退。
- win `GeminiService.cs:141-163` 自己重复 P/Invoke 了一遍 CredRead/CredFree，应复用 `CredentialSecretStore`。

### 18. win 两套日志两个目录

`Services/Log.cs` 写 `%APPDATA%\TokenBar\tokenbar.log`（2MB 轮转）；`App.xaml.cs:166-179` 私有 Log() 写 `%LOCALAPPDATA%\TokenBar\app.log`（无轮转）。且 `DispatcherUnhandledException` 一律 `e.Handled = true` 静默吞掉所有 UI 异常。

### 19. win 模型层耦合 WPF

`TokenQuota.cs:4` `using System.Windows.Media`，`StatusBrush`/`GetThemeBrush` 在模型里返回 `SolidColorBrush`，导致测试工程被迫 `UseWPF+UseWindowsForms`。画刷映射应放 Helpers/Views 层。

### 20. 稳态无失败退避

首刷的两次重试（15s/45s）之后，若网络持续故障，只按固定间隔硬打（1 分钟间隔 × 10 个厂商全失败 = 每分钟 10 次无效请求）。建议连续失败轮次后临时拉长间隔。

### 21. 零散小项

- mac `postLowBalanceNotification` 每次发通知都重新 `requestAuthorization`，应缓存授权结果（RefreshManager.swift:1298-1314）。
- mac `parseDurationString` 工具函数住在 OpenAIService 里，被 Kimi/DeepSeek/Volcengine/Custom 4 处跨调，应移到 `RateLimitReset`。
- mac `lastRoundOutcome.allFailed` 的 count 用 `split(separator:",")` 反算，custom×N 被算成 1 个（仅展示用途，RefreshManager.swift:508）。
- mac `runLoginViaAppleScript` 在主线程同步执行 NSAppleScript，Terminal 无响应时短暂冻结 UI（低频，影响小）。
- win `TrayIconManager.cs:203-206` 菜单项 async lambda 无 try/catch，目前靠被调方吞异常保平安——脆弱。
- win fire-and-forget `_ =` 共 6 处（RefreshManager.cs:135,1530,1546,1556；SettingsWindow.xaml.cs:1013,1462），一旦传入可取消 token 会产生未观察异常。
- mac 少量 force unwrap 可消除：GeminiService.swift:960,967 `remainingFraction!`（应改 guard let 绑定）等。
- mac I18n.swift：300+ case 枚举 + 单个 530 行 switch，编译期穷尽保证不漏翻，但无法用 .strings/.xcstrings 工具链、无法让非开发者参与翻译；`effectiveLanguage == "zh"` 判断散落全库约 40 处。
- win LocalizationManager.cs（~160 属性）与 mac I18n.swift 同 key 集合纯手工同步；此外两端还各有 ~30-70 处内联 `isZh ?:` 三元绕过翻译系统——i18n 实际是三重维护负担。

## 实施建议顺序

1. **第一批（P0，改动小、收益确定）**：修 #1-#10 共 10 个确认 Bug。
2. **第二批**：#14 窗口标题语义化（防止未来静默破坏英文界面）+ #15 win 隐藏窗口跳过渲染。
3. **第三批（单独规划、分批做）**：#11-#13 Provider 抽象层 + RefreshManager 表驱动 + SettingsView 拆分——工作量大，建议两端同步收敛以免继续漂移。
4. **穿插进行**：#16-#17 测试补强，优先给 RefreshManager 核心机制和 win 端 private 解析器补测。
