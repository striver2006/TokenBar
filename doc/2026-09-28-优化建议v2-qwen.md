# TokenBar 代码审查与优化建议 v2

> 日期：2026-09-28
> 范围：macOS 端（mac/Sources/TokenBar/）+ Windows 端（windows/src/TokenBar/）全量审查
> 状态：建议稿 v2，未实施
> 版本说明：v2 依据 `doc/2026-09-28-优化建议审核-glm.md`（GLM/ZCode 审核意见）修订——
> ① 修正全部计数偏差（#3/#6/#11/#13/#21 等，多数比 v1 更严重）；
> ② **删除 v1 中不成立的推论**「mac 刷新体 JSON 解析全在主线程串行」（非隔离服务实际在后台执行器运行）；
> ③ 更正 #13 故障注释引据；
> ④ 新增审核发现的现存实锤：英文模式下 mac OpenRouter 状态卡当前真实漏中文；
> ⑤ 按审核意见重排实施顺序（P0 批内按风险排序、并发修复前先补 RefreshManager 机制测试、表驱动收窄到六个简单厂商）。

## 总体评价

基础设施层质量明显高于平均水平：密钥三态读写（防"读不到→误删"）、CAS 刷新闸门、generation 防脏写、共享 HttpClient、原子写 settings.json、两端共享测试黄金向量，这些都很规范（经审核复核确认，包括明文兜底为设计内取舍、日志纪律良好等易误判点）。主要问题集中在：**确认的并发/资源 Bug（Windows 端为主）**、**Provider Service 层大量模板复制（实测比 v1 统计更多）**、**巨石 UI 文件**、**I18n 双轨制**、以及**编排层测试零覆盖**。

审核结论：v1 的 21 个编号问题**无一误报**，可作为实施依据；v2 为其修正版。

## P1 · 结构性重复（最大的维护负担，实测份数普遍比 v1 统计更多）

### 11. 九个 Provider Service 无统一抽象，模板代码大量复制（两端同病）

没有 `QuotaProvider` 之类的协议/接口，每个 Service 都是独立 singleton + 不同形状的元组返回值。审核实测修正后的重复清单：

| 重复项 | 实测份数 | 备注 |
|---|---|---|
| `getHeader`/`GetHeader` 大小写不敏感取响应头闭包 | mac **7 份**（6 文件，CustomProviderService 内 2 份）、win **8 份**（含 GeminiService.cs:374） | 且完全多余——`HTTPURLResponse.value(forHTTPHeaderField:)` 本身大小写不敏感（GLMService.swift:64-70、GeminiService.swift:1077 已在直接用系统 API） |
| endpoint trim + 去尾斜杠块 | mac **9 份**（含 KimiService.swift:171-174） | — |
| 401/429/非 2xx 三段式错误处理 + `isZh ?:` 内联 | mac **8 处** / win **9 处** | **经全链路核实绕过 I18n 系统**：抛错点就地双语 → RefreshManager catch 后原样塞入 errorMessage → UI 直出，不存在任何"错误字符串→本地化"映射层；与 RefreshManager 的 I18nKey 是两套并行机制 |
| x-ratelimit 三头 → TPM 窗口构造块 | mac **5 份** / win **5 份**（含 CustomProviderService.cs:181-208）；另有 anthropic-ratelimit 同构变体 mac 2 处 / win 2 处 | 连 clamp 表达式都逐字相同 |
| 余额查询重复实现 | DeepSeek 版**除函数名外逐字相同**；Kimi/Moonshot 约 85-90% 相似 | 差异仅可配置端点与 cash_balance 兜底 |
| key 尾号掩码 | mac **6 份** + win **6 份** | 另有 GeminiService.swift:1106 无守卫变体 |

**建议方向（审核认可）**：抽 `protocol QuotaFetching`（win 端对应 interface）+ 共享的 `RateLimitHeaderParser`、`EndpointNormalizer`、`ProviderError`（携带 I18nKey 而非内联双语文案），两端同步收敛。

### 12. RefreshManager 两端各 10 个 `refreshXxx()` —— 表驱动改造**只适用于六个简单厂商**

- mac：`RefreshManager.swift:636-1259`；win：`RefreshManager.cs:796-1449`。
- 审核修正：**六个简单厂商**（GLM/OpenAI/DeepSeek/Volcengine/Kimi/OpenRouter）实际 36-51 行/个，逐段对比差异只剩 ProviderType 枚举、settings 字段名、I18n 键、槽位映射——"几乎只差字段名"精确成立；**Claude/Gemini/Aliyun/Custom 为 75-120 行、含实质分支**（双通道回退、凭证合并、钥匙串预取、双槽位余额判别），并非模板复制。
- **实施含义（审核意见）**：表驱动收敛六个简单厂商收益明确；四个复杂厂商应保留显式特例，不要硬塞进表。
- win 端该文件职责堆积核实：定时器（:497-530,:635-645）、网络监听（:178-204）、settings 持久化（:420-495）、凭据同步编排（:218-392，注：CredWrite/CredDelete 的 P/Invoke 在 SecretStore.cs:182-189，本文件只做编排）、余额状态机+托盘气泡（:1456-1503）、本地导入（:1505-1534）——至少 SettingsStore、SecretSync、BalanceMonitor 可拆出。

### 13. SettingsView.swift（2651 行）巨石文件

- 12 个 tab（其中 3 个为非厂商 tab：自定义/排序/通用）全部内联在一个 struct：**60 个 @State**（:19-105，v1 误估 ~35）+ 25 条 settings→input 的 onChange 反向同步（:260-284）+ tab UI（:399-2594）。
- 每个厂商 tab 是 130-200 行的同构模板（标题卡 + 状态卡 + SecureField/eye 切换 + endpoint + 保存并测试按钮）。
- **新增一个设置字段实测要改 6-8 处**（mac 端：AppSettings/@State/syncFromSettings/onChange/tab UI/保存按钮赋值/I18n 键，凭证还要动 AppSecrets+钥匙串），**双端合计 10+ 处**。
- 引据更正（审核）：:294-301 注释记录的真实故障是「Picker 叠加 `.id(language)` 致 onChange 基线重置、`saveSettings()` 未触发，刷新间隔 5→1 分钟后近 3 小时未生效」——属**保存链路失效**而非 v1 所说"新增字段漏同步"，但同属手工同步清单脆弱性的直接证据，结论不变。
- 混合职责：`ProviderTabPicker`（NSViewRepresentable）、`startGeminiGoogleLogin`、`saveAliyunAccessKeyAndTest` 等业务编排也在同一文件。

**建议方向**：拆成每 tab 一个子 View（自带自己的 @State），直接消掉三份手工同步清单。

同类问题：
- `GeminiService.swift`（1115 行）一个 actor 负责七件事（OAuth client 发现、loopback 登录、token 刷新候选循环、Antigravity 配额 API、AI Studio Key、本地文件解析、凭证合并），凭证获取子系统适合独立成 `GeminiCredentialResolver`。
- win 端卡片构造重复的定位更正（审核）：**最大重复在 PopoverWindow 内部**——`CreateProviderCard`(:168-375) vs `CreateCustomProviderCard`(:377-540) 约八成同构；跨文件是模式级重复（icon badge 三抄、状态点配色、Border 样式常量）。SettingsWindow 的厂商状态卡本体是 XAML 静态元素 + UpdateOne 填 TextBlock，并非代码构造。`SettingsWindow.xaml.cs` 1471 行的体量主要来自保存/测试编排而非画卡片。

### 14. 窗口标题用中文串当翻译 key —— 已有现存漏译实锤

机制（两端核实）：
- mac `TokenQuota.swift:168-195` `localizedTitle` 靠匹配中文标题反译（含 `"可用模型 ("` 前缀裁剪），default 分支返回中文原文。
- win `TokenQuota.cs:127-168` 同款，`BadgeLabel` 靠 `Contains("月")/Contains("周")` 推断。

**审核新增实锤（现存 bug）**：mac `OpenRouterService.swift:111` 设置的「OpenRouter 连接正常」**未登记**进 mac 反译表，而 win 端 `TokenQuota.cs:153` 已登记——**英文模式下 mac 弹窗的 OpenRouter 状态卡当前真实显示中文**，且两端登记表已经漂移。

**建议**：① 立即补上这个 case（1 行修复，不必等重构）；② 中期把 Title 改语义枚举（`enum WindowTitle { case fiveHour, weekly, monthly, status, ... }`）随 TokenWindow 持久化，显示层再翻译。

## P2 · UI 性能（win）

### 15. Popover 隐藏时仍全量重建视觉树（全链路核实）

- 链路：Closing 被拦成 Hide（PopoverWindow.xaml.cs:44-49，仅 ForceClose :60-64 真关闭）→ Closed 永不触发 → OnQuotasUpdated 订阅常驻（:32-35,:51-57）→ `UpdateTexts` 末尾无条件 `RenderCards()`（:84）→ 先 `Children.Clear()` 再全量 new（:87-166，无复用/diff）。
- 触发次数精确核算：**9 个内置厂商全开时一轮恰 20 次**（round begin/end + 每厂商入口/收尾各 1），每启用一个自定义厂商再加 2。
- SettingsWindow.UpdateStatuses:651 无条件调 `RenderCustomProvidersList()`（不看当前 tab）。

**建议方向（审核认可）**：不可见时跳过渲染——IsVisible 检查或 dirty 标记是低风险首选；中期可改 ItemsControl+DataTemplate 增量更新。

### ~~mac 刷新体全在主线程~~（v2 删除）

v1 此处推断"9+ 个厂商的 JSON 解析、窗口构造全部在主线程串行"，经审核**不成立**：各 Service 均为非隔离类型（`@unchecked Sendable` 类或独立 actor），Swift 并发语义下非隔离 async 函数在 await 处跳出 MainActor 到全局并发执行器，解析与窗口构造实际在后台线程执行（ClaudeService.swift:30-31 有明确注释并把本地 JSON 解析挪进 `Task.detached`；GeminiService 是独立 actor）。真正留在主线程的只有 RefreshManager 自身的编排段、`commit()` 写回、`processBalance`、`finishTimedOutProvider`，当前体量无碍。**不构成需要整改的问题。**

## P3 · 测试补强

### 16. 编排层与网络层零覆盖（先于并发修复实施）

- 所有 Service 的 HTTP 层：mac 全库 URLProtocol 0 命中，401/429 分类、响应头解析无测试。
- win 端多数解析器是 `private` 测试够不到：ClaudeService（`TryParseUtc`/`ParseScopedWeeklyLimit` 均 private，主解析内联且直读真实 `~/.claude.json`）、GeminiService.cs:681 `ParseQuotaBucket`、GLMService.cs:187 解析内联（含秒/毫秒量级判断——恰是与 mac 有分类顺序差异的地方）。

**建议方向（审核认可，性价比高）**：
1. **顺序前置（审核意见）**：动 P0 的 #6/#7/#8 之前，先给 RefreshManager 补最小机制测试——闸门抢占、generation 丢弃、超时收尾三个场景即可，否则并发修复没有回归网。

### 17. mac 132 个测试集中在一个 2105 行文件

单个 `final class TokenBarTests`（另有 ProviderLogoTests.swift 3 测、SingleInstanceGuardTests.swift 2 测两个小文件），按模块拆分是零成本改进。另建议加一条 **I18nKey 一致性测试**（每个 key 在 zh/en 下均非空且 ≠ rawValue），低成本高价值。

## P4 · 安全与其他

### 密钥存储（现状良好，两点需知悉）

- mac：钥匙串（`kSecAttrAccessibleAfterFirstUnlock`）；win：Win32 凭据管理器（受 DPAPI 保护，选型理由见 SecretStore.cs:78-81 注释）。三态读写、防误删设计扎实。
- 日志纪律复核通过：两端未发现 key/token 插值进日志（mac os_log 带 privacy 标注；win 116 处 Log 调用逐一排查无敏感值）。唯一边缘：错误消息内嵌响应体前 100-300 字符，属异常消息且不含凭证本体。
- **明文兜底是设计内取舍但风险真实**：钥匙串/凭据管理器不可用时，全部 API Key、OAuth token（含 claudeToken、geminiRefreshToken 等长效凭证）、控制台 Cookie 明文写入 plist / settings.json（mac TokenQuota.swift:953-964；win AppSettings.cs:136-140）。**审核提醒**：若改为"长效 OAuth 凭证不回退明文"，会改变"宁明文不丢凭证"的既定取舍（注释自述），应做成用户可见的选项或至少保留告警，**不要静默改语义**。
- win `GeminiService.cs:140-190` 重复 P/Invoke CredRead/CredFree，SecretStore.cs:79-80 注释自认"已知重复"——记录在案的技术债，应复用 `CredentialSecretStore`。

### 18. win 两套日志两个目录

`Services/Log.cs` 写 `%APPDATA%\TokenBar\tokenbar.log`（2MB 轮转）；`App.xaml.cs:166-179` 私有 Log() 写 `%LOCALAPPDATA%\TokenBar\app.log`（无轮转）。且 `App.xaml.cs:34` `DispatcherUnhandledException` 无条件 `e.Handled = true` 静默吞掉所有 UI 异常。

### 19. win 模型层耦合 WPF
